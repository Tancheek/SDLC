# Локальный двухстадийный конвейер SVS → RVC на ONNX Runtime

## Контекст и постановка задачи

SVS-RVC должен синтезировать вокальную партию по MIDI-партитуре и тексту и переносить тембр выбранной RVC-модели. Ключевые ограничения проекта: обработка выполняется **локально**, без обязательного сетевого подключения и передачи голосовых данных в облако (REQ-SEC-001); real-time-мониторинг должен укладываться в задержку **не более 250 мс** при буфере 128–256 сэмплов (REQ-PERF-001); качество тембра и разборчивость слов должны сохраняться (REQ-FUNC-003). Целевое оборудование — ноутбук с 8 ядрами, 16 ГБ ОЗУ и AVX2 **без дискретной GPU**.

Как организовать inference SVS- и RVC-моделей, чтобы обеспечить локальность, приемлемую задержку и качество на CPU, не увеличивая существенно сложность сборки и сопровождения Windows-приложения?

## Драйверы решения

* **Локальность и конфиденциальность.** Голосовые данные, текст и модели не должны покидать машину пользователя (REQ-SEC-001).
* **Задержка real-time.** Целевой бюджет — не более 250 мс при буфере 128–256 сэмплов; конвейер не должен добавлять неконтролируемые задержки (REQ-PERF-001).
* **Качество тембра.** Нужно сохранить мелодию, длительности, вибрато/портаменто и разборчивость слов (REQ-FUNC-003, BR-04).
* **Ограничения оборудования.** 8 ядер CPU, 16 ГБ ОЗУ, AVX2, без GPU; решение должно работать на типовом ноутбуке.
* **Готовые модели.** Проект использует готовые SVS- и RVC-модели; обучение не выполняется (SRS, раздел 2.3).
* **Стоимость и сроки.** MVP должен быть реализован за 10 человеко-дней (две недели, один разработчик); облачная инфраструктура и обучение моделей не входят в бюджет.
* **Сопровождение.** Сборка под Windows 10/11 x64 должна оставаться переносимой, без тяжёлого Python/PyTorch runtime.

## Рассмотренные варианты

* **Локальный двухстадийный конвейер SVS → RVC на ONNX Runtime.** SVS-модель формирует вокальный сигнал по нотам, фонемам и F0; RVC-модель переносит тембр; обе модели исполняются в ONNX Runtime с CPU execution provider.
* **Облачный API синтеза и RVC.** Приложение отправляет MIDI, текст и параметры на внешний сервис, получает готовый аудиофайл.
* **Единая end-to-end модель SVS + RVC.** Одна нейросеть непосредственно генерирует вокальный сигнал с целевым тембром по партитуре и тексту.
* **Встроенный PyTorch runtime с локальными моделями.** Приложение несёт с собой PyTorch и исполняет исходные модели на CPU.

## Итог решения

Выбран вариант **«Локальный двухстадийный конвейер SVS → RVC на ONNX Runtime»**, потому что только он одновременно удовлетворяет жёсткому требованию локальности (REQ-SEC-001), укладывается в бюджет задержки real-time на CPU (REQ-PERF-001) и позволяет использовать готовые RVC-модели без обучения (REQ-FUNC-003). Облачный API нарушает локальность и добавляет зависимость от сети и подписки; единая end-to-end модель требует обучения и не поддерживает существующую библиотеку тембров; PyTorch runtime существенно увеличивает размер поставки и сложность сборки под Windows.

**Архитектура конвейера.**

1. `MidiImporter` и `LyricsAligner` формируют `AlignedScore`: ноты, длительности, слоги, язык.
2. `PhonemeConverter` преобразует текст в фонемы; `F0Builder` строит F0-контур с вибрато, портаменто и глиссандо.
3. `SvsEngine` исполняет SVS-модель в ONNX Runtime и получает вокальный сигнал в рабочей частоте 48 кГц.
4. `RvcConverter` извлекает ContentVec/HuBERT-признаки, выполняет индексный поиск по выбранной RVC-модели и переносит тембр.
5. `AudioPostProcessor` нормализует сигнал, ограничивает клиппинг и сглаживает переходы.
6. `AudioExporter` записывает WAV/FLAC; `AudioDevice` выводит preview/real-time.

**Режимы работы.**

* **Офлайн-рендер.** Полная партия обрабатывается блоками; приоритет — качество, допускается время рендера больше реального.
* **Real-time-мониторинг.** Пайплайн работает чанками с look-ahead; при нехватке времени буфер увеличивается до 256 сэмплов, а качество preview может быть снижено. Целевая задержка — ≤ 250 мс.

**Оптимизация под CPU.**

* ONNX Runtime CPU execution provider, intra-op parallelism по числу физических ядер (до 8), межоперационный параллелизм ограничен, чтобы не конкурировать с аудиопотоком.
* Граф-оптимизация ONNX (`ORT_ENABLE_ALL`), FP32 для качества; для preview допускается динамическое квантование в INT8 при сохранении приемлемого качества.
* Кэширование ContentVec/HuBERT-признаков для повторного рендера того же фрагмента.
* Разделение потоков: аудио-поток с высоким приоритетом, inference — в пуле рабочих потоков.

### Последствия

* **Хорошо:** данные и модели остаются локально; нет сетевых задержек, подписок и утечек голосовых данных.
* **Хорошо:** двухстадийная схема позволяет менять RVC-тембр без переобучения SVS и использовать существующую библиотеку моделей.
* **Хорошо:** ONNX Runtime упрощает поставку по сравнению с PyTorch и работает на CPU с AVX2.
* **Плохо:** две стадии увеличивают суммарную задержку и потребление памяти; для real-time требуется тщательная оптимизация и, возможно, preview-режим с меньшим качеством.
* **Плохо:** не все операции RVC-моделей могут быть корректно экспортированы в ONNX; требуется проверка совместимости и, возможно, замена отдельных слоёв.
* **Плохо:** качество на CPU может уступать GPU-инференсу; для сложных партий рендер будет заметно медленнее реального времени.
* **Риск:** лицензии голосовых моделей и права на голосовые данные остаются ответственностью пользователя; приложение должно показывать лицензию модели.

### Подтверждение

* **Локальность:** тест с сетевым монитором/брандмауэром подтверждает отсутствие исходящих соединений при импорте, рендере и экспорте (REQ-SEC-001).
* **Задержка:** измерение сквозной задержки real-time-режима при буфере 128 и 256 сэмплов; критерий — ≤ 250 мс (REQ-PERF-001).
* **Качество:** слепое прослушивание не менее чем тремя слушателями; критерий — ≥ 2 из 3 узнают тембр, разборчивость ≥ 4/5 (BR-04).
* **Совместимость моделей:** тесты с валидной, повреждённой и несовместимой моделью; рендер с некорректной моделью должен блокироваться (REQ-FUNC-002).
* **Ресурсы:** профилирование CPU и памяти на целевом ноутбуке; отсутствие OOM и деградации UI при 3-минутной партии.

## Плюсы и минусы вариантов

### Локальный двухстадийный конвейер SVS → RVC на ONNX Runtime

SVS- и RVC-модели исполняются локально в ONNX Runtime; приложение не обращается к сети.

* Хорошо, потому что полностью соблюдает REQ-SEC-001 и не зависит от доступности облака.
* Хорошо, потому что использует готовые RVC-модели и позволяет менять тембр без обучения.
* Хорошо, потому что ONNX Runtime легче PyTorch и поддерживает CPU-оптимизации.
* Нейтрально, потому что требует конвертации моделей в ONNX и проверки совместимости.
* Плохо, потому что две стадии увеличивают задержку и нагрузку на CPU.
* Плохо, потому что real-time на слабом ноутбуке может требовать снижения качества preview.

### Облачный API синтеза и RVC

MIDI, текст и параметры отправляются на сервер, результат возвращается аудиофайлом.

* Хорошо, потому что снимает нагрузку с CPU и упрощает клиент.
* Хорошо, потому что качество может быть выше за счёт GPU сервера.
* Плохо, потому что нарушает REQ-SEC-001: голосовые данные и текст покидают машину пользователя.
* Плохо, потому что зависит от сети, подписки и доступности сервиса.
* Плохо, потому что добавляет задержку сети и не подходит для real-time с бюджетом 250 мс.
* Плохо, потому что требует договоров, биллинга и защиты персональных данных.

### Единая end-to-end модель SVS + RVC

Одна модель генерирует вокальный сигнал с целевым тембром непосредственно по партитуре и тексту.

* Хорошо, потому что потенциально даёт лучшую согласованность тембра и просодии.
* Хорошо, потому что упрощает конвейер и снижает задержку.
* Плохо, потому что требует обучения на голосовых данных и не использует готовые RVC-модели.
* Плохо, потому что каждый новый тембр требует отдельной модели или fine-tuning.
* Плохо, потому что выходит за границы MVP и увеличивает сроки и стоимость.
* Плохо, потому что качество и стабильность такой модели сложнее проверить.

### Встроенный PyTorch runtime с локальными моделями

Приложение поставляет PyTorch и исполняет исходные SVS/RVC-модели на CPU.

* Хорошо, потому что не требует конвертации в ONNX и поддерживает больше операций.
* Хорошо, потому что упрощает отладку моделей в исходном виде.
* Плохо, потому что существенно увеличивает размер дистрибутива и время запуска.
* Плохо, потому что усложняет сборку и сопровождение под Windows.
* Плохо, потому что CPU-инференс PyTorch обычно медленнее оптимизированного ONNX Runtime.
* Плохо, потому что тянет Python-зависимости и конфликты версий.

## Дополнительная информация

* Решение связано с требованиями REQ-FUNC-002, REQ-FUNC-003, REQ-PERF-001, REQ-SEC-001 и бизнес-требованиями BR-04, BR-05.
* Решение раскрывается в SDD: DV-002 (компоненты `SvsEngine`, `RvcConverter`, `OnnxModelLoader`), DV-003 (контракты `ISynthesisPipeline`), DV-004 (сценарии рендера и real-time), DV-005 (состояния рендера), DV-006 (зависимость от ONNX Runtime).
* Проверка совместимости моделей выполняется до рендера: манифест `model.json` содержит версию, частоту, список ONNX-файлов и SHA-256.
* Решение может быть пересмотрено при появлении GPU-ускорения (DirectML/CUDA) или при переходе на единую модель; триггер пересмотра — стабильное превышение задержки 250 мс или недостаточное качество на целевом оборудовании.
