# Локальный двухстадийный конвейер SVS → RVC на ONNX Runtime

## Контекст и постановка задачи

SVS-RVC синтезирует вокальную партию по MIDI-партитуре и тексту и переносит тембр выбранной RVC-модели. Ключевые ограничения: обработка выполняется **локально**, без передачи голосовых данных в облако (REQ-SEC-001); real-time-мониторинг укладывается в задержку **не более 250 мс** при буфере 128–256 сэмплов (REQ-PERF-001); качество тембра и разборчивость слов сохраняются (REQ-FUNC-003). Целевое оборудование — ноутбук с 8 ядрами, 16 ГБ ОЗУ и AVX2 **без дискретной GPU**.

Как организовать inference SVS- и RVC-моделей, чтобы обеспечить локальность, приемлемую задержку и качество на CPU, не увеличивая существенно сложность сборки и сопровождения Windows-приложения?

## Драйверы решения

* **Локальность и конфиденциальность.** Голосовые данные, текст и модели не должны покидать машину пользователя (REQ-SEC-001).
* **Задержка real-time.** Бюджет — не более 250 мс при буфере 128–256 сэмплов; конвейер не должен добавлять неконтролируемые задержки (REQ-PERF-001).
* **Качество тембра.** Мелодия, длительности, вибрато/портаменто и разборчивость слов должны сохраняться (REQ-FUNC-003, BR-04).
* **Ограничения оборудования.** 8 ядер CPU, 16 ГБ ОЗУ, AVX2, без GPU; решение должно работать на типовом ноутбуке.
* **Готовые модели.** Используются готовые SVS- и RVC-модели, обучение не выполняется.
* **Сроки и сопровождение.** MVP — 10 человеко-дней, один разработчик; переносимая сборка под Windows 10/11 x64 без Python/PyTorch runtime.

## Рассмотренные варианты

* **Локальный двухстадийный конвейер SVS → RVC на ONNX Runtime.** SVS-модель формирует вокальный сигнал по нотам, фонемам и F0; RVC-модель переносит тембр; обе исполняются в ONNX Runtime с CPU execution provider.
* **Облачный API синтеза и RVC.** MIDI, текст и параметры отправляются на внешний сервис, результат возвращается аудиофайлом.
* **Единая end-to-end модель SVS + RVC.** Одна сеть генерирует вокальный сигнал с целевым тембром по партитуре и тексту.
* **Встроенный PyTorch runtime.** Приложение поставляет PyTorch и исполняет исходные модели на CPU.

## Итог решения

Выбран вариант **«Локальный двухстадийный конвейер SVS → RVC на ONNX Runtime»**: только он одновременно удовлетворяет требованию локальности (REQ-SEC-001), укладывается в бюджет задержки real-time на CPU (REQ-PERF-001) и позволяет использовать готовые RVC-модели без обучения (REQ-FUNC-003). Облачный API нарушает локальность и зависит от сети; единая end-to-end модель требует обучения и не поддерживает существующую библиотеку тембров; PyTorch runtime увеличивает размер поставки и сложность сборки.

* Конвейер: `MidiImporter` + `LyricsAligner` → `PhonemeConverter` + `F0Builder` → `SvsEngine` → `RvcConverter` → `AudioPostProcessor` → `AudioExporter`.
* Режимы: офлайн-рендер блоками с приоритетом качества; real-time чанками с look-ahead, буфер до 256 сэмплов. ONNX Runtime CPU provider, FP32 (для preview допустим INT8).

### Последствия

* **Хорошо:** данные и модели остаются локально; нет сетевых задержек, подписок и утечек голосовых данных.
* **Хорошо:** смена RVC-тембра не требует переобучения SVS и использует готовую библиотеку моделей.
* **Хорошо:** ONNX Runtime проще PyTorch в поставке и работает на CPU с AVX2.
* **Плохо:** две стадии увеличивают задержку и потребление памяти; для real-time нужна тщательная оптимизация и, возможно, preview с меньшим качеством.
* **Плохо:** не все операции RVC-моделей корректно экспортируются в ONNX; качество на CPU может уступать GPU.
* **Риск:** лицензии голосовых моделей и права на данные остаются ответственностью пользователя; приложение показывает лицензию модели.

### Подтверждение

* **Локальность:** сетевой монитор/брандмауэр не фиксирует исходящих соединений при импорте, рендере и экспорте (REQ-SEC-001).
* **Задержка:** измерение сквозной задержки при буфере 128 и 256 сэмплов; критерий — ≤ 250 мс (REQ-PERF-001).
* **Качество:** слепое прослушивание не менее чем тремя слушателями; критерий — ≥ 2 из 3 узнают тембр, разборчивость ≥ 4/5 (BR-04).
* **Совместимость моделей:** тесты с валидной, повреждённой и несовместимой моделью; рендер с некорректной моделью блокируется (REQ-FUNC-002).
* **Ресурсы:** профилирование CPU и памяти на целевом ноутбуке при 3-минутной партии, без OOM и деградации UI.

## Плюсы и минусы вариантов

### Локальный двухстадийный конвейер SVS → RVC на ONNX Runtime

* Хорошо, потому что полностью соблюдает REQ-SEC-001 и не зависит от доступности облака.
* Хорошо, потому что использует готовые RVC-модели и позволяет менять тембр без обучения.
* Хорошо, потому что ONNX Runtime легче PyTorch и поддерживает CPU-оптимизации.
* Нейтрально, потому что требует конвертации моделей в ONNX и проверки совместимости.
* Плохо, потому что две стадии увеличивают задержку и нагрузку на CPU; real-time на слабом ноутбуке может требовать снижения качества preview.

### Облачный API синтеза и RVC

* Хорошо, потому что снимает нагрузку с CPU и упрощает клиент.
* Хорошо, потому что качество может быть выше за счёт GPU сервера.
* Плохо, потому что нарушает REQ-SEC-001: голосовые данные и текст покидают машину пользователя.
* Плохо, потому что зависит от сети, подписки и доступности сервиса.
* Плохо, потому что добавляет сетевую задержку и не подходит для real-time с бюджетом 250 мс; требует договоров, биллинга и защиты персональных данных.

### Единая end-to-end модель SVS + RVC

* Хорошо, потому что потенциально даёт лучшую согласованность тембра и просодии, упрощает конвейер и снижает задержку.
* Плохо, потому что требует обучения на голосовых данных и не использует готовые RVC-модели.
* Плохо, потому что каждый новый тембр требует отдельной модели или fine-tuning.
* Плохо, потому что выходит за границы MVP, увеличивает сроки и стоимость; качество сложнее проверить.

### Встроенный PyTorch runtime с локальными моделями

* Хорошо, потому что не требует конвертации в ONNX и поддерживает больше операций.
* Хорошо, потому что упрощает отладку моделей в исходном виде.
* Плохо, потому что увеличивает размер дистрибутива и время запуска.
* Плохо, потому что усложняет сборку и сопровождение под Windows, тянет Python-зависимости и конфликты версий.
* Плохо, потому что CPU-инференс PyTorch обычно медленнее оптимизированного ONNX Runtime.

## Дополнительная информация

* Связанные требования: REQ-FUNC-002, REQ-FUNC-003, REQ-PERF-001, REQ-SEC-001; BR-04, BR-05.
* Раскрытие в SDD: DV-002 (компоненты `SvsEngine`, `RvcConverter`, `OnnxModelLoader`), DV-003 (контракт `ISynthesisPipeline`), DV-004 (рендер и real-time), DV-005 (состояния рендера), DV-006 (зависимость от ONNX Runtime).
* Совместимость моделей проверяется до рендера: манифест `model.json` содержит версию, частоту, список ONNX-файлов и SHA-256.
* Пересмотр — при появлении GPU-ускорения (DirectML/CUDA) или переходе на единую модель; триггер — стабильное превышение задержки 250 мс или недостаточное качество на целевом оборудовании.
