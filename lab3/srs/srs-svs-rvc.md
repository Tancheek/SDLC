## 1. Введение {#1-introduction}

Документ фиксирует верифицируемые требования к системе SVS-RVC: офлайн- и real-time-синтез поющего голоса по нотной партитуре с текстом и перенос тембра целевого певца методом RVC. Ядро — C++; пользовательские интерфейсы — CLI и десктопный GUI.

### 1.1 Назначение документа {#11-document-purpose}

SRS определяет, **что** должна делать система, а не как она реализована. Аудитории: разработка (проектирование ядра и GUI), QA (тест-планы и приёмочные критерии), специалисты по ML (обучение и версионирование моделей тембра), владельцы голосовых данных и compliance-роли (согласия, лицензии). Документ сопровождает продукт на всём жизненном цикле и является основой приёмки версий 0.1–1.0. Связанные документы: карточки моделей RVC, тест-наборы, лицензии на голосовые данные.

### 1.2 Область применения продукта {#12-product-scope}

SVS-RVC — десктопное приложение и C++ библиотека для создания вокальной партии: на входе MIDI-партитура (ноты, длительности, сила) и текст (лирика, слоги), на выходе — WAV-аудио поющего голоса с тембром, взятым из обученной модели RVC. Два режима: пакетный офлайн-рендер всей песни и live-мониторинг (озвучивание партии в реальном времени). В область входят: фонетический фронтенд, F0-контур, акустический синтез, конверсия тембра RVC, DSP-постобработка, экспорт, локальное управление моделями. НЕ входят: обучение новых моделей с нуля (используются готовые RVC-чекпойнты), распознавание аудио-вокала (autotune/cover из записи), облачный сервис и мобильные платформы.

### 1.3 Определения, акронимы и сокращения {#13-definitions-acronyms-and-abbreviations}

| Term | Definition |
|------|------------|
| SVS | Singing Voice Synthesis — синтез поющего голоса по партитуре и тексту |
| SVC | Singing Voice Conversion — конверсия тембра вокальной записи с сохранением мелодии и текста |
| RVC | Retrieval-based Voice Conversion — метод конверсии тембра с поиском по индексной базе признаков |
| F0 | Основная частота голоса (мелодическая линия), Гц |

| RMVPE / CREPE | Алгоритмы оценки F0; в проекте используются как ONNX-модели |

| RTF | Real-Time Factor — отношение времени обработки к длительности аудио |

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

Продукт — самостоятельное десктопное приложение, встраиваемое ядро которого (C++ библиотека) может использоваться как компонент в других инструментах. Внешние связи: пользователь (CLI/GUI), аудиоустройство ОС, файловая система (MIDI/текст/модели/аудио), опционально GPU-рантайм. Владелец продукта — {{организация}}. Поддержка: локальная, без сетевых сервисов и SLA. Зависимость верхнего уровня — качество и лицензия пользовательских RVC-моделей.

#### Бизнес-цели

| ID | Бизнес-цель | Метрика успеха |
|----|-------------|----------------|
| BG-1 | Сократить время создания вокального демо | 3-минутная партия рендерится и принимается ≤ 30 мин (исходный процесс с вокалистом — 8–12 ч) |
| BG-2 | Снизить стоимость демо-записи | Затраты на демо ≤ 30 % от стоимости сессии вокалиста |
| BG-3 | Дать доступ к разным тембрам без найма исполнителя | ≥ 70 % демо принимаются заказчиком без перезаписи вокала |
| BG-4 | Обеспечить юридическую чистоту AI-вокала | 100 % экспортов имеют подтверждённое согласие владельца голоса и маркировку «синтезировано» |


### 2.2 Функции продукта {#22-product-functions}

1. Импорт партитуры: MIDI + лирика (слоги, привязка к нотам).
2. Фонетический фронтенд: нормализация текста, фонемы, длительности, расстановка согласных/гласных по нотам.
3. Мелодический контроль: F0 из нот, глиссандо, вибрато, портаменто, тональность/строй.
4. Акустический синтез: генерация вокального сигнала (mel + F0 → волновая форма).
5. Перенос тембра RVC: извлечение контент-признаков (HuBERT/ContentVec), F0, поиск по индексной базе, генератор целевого тембра.
6. DSP-постобработка: ресемплинг, формантный/питч-сдвиг, дыхание/шум, эквалайзер, компрессия, нормализация громкости.
7. Два режима: офлайн-рендер и real-time-мониторинг с низкой задержкой.
8. Экспорт: WAV/FLAC, разбиение по тактам, стем вокала, микс-превью.
9. Управление моделями: импорт/выбор RVC-чекпойнтов и индексов, их проверка и версионирование.
10. Диагностика: логи, метрики RTF/XRUN, отчёты о качестве синтеза.

### 2.3 Ограничения продукта {#23-product-constraints}

- Ядро синтеза и переноса тембра **должно** быть реализовано на C++ (стандарт не ниже C++17).
- Перенос тембра **должен** выполняться методом RVC (HuBERT/ContentVec + индексный поиск + генератор), без подмены другими методами в релизе 1.0.
- Вычисления **должны** выполняться локально, без обязательного сетевого подключения.
- Поддерживаемые ОС: Windows 10/11 x64, Linux x64; GPU — опционально.
- Обучение моделей — вне системы: используются готовые чекпойнты RVC v2 (32k/40k/48k).
- В real-time режиме **запрещена** обработка с доступом к «будущим» сэмплам (причинность).
- Голосовые данные **должны** иметь подтверждённое согласие владельца (см. 3.6).

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

| Допущение/зависимость | Влияние при нарушении |
|-----------------------|-----------------------|

## 3. Требования {#3-requirements}

Формат требования: **ID** — уникальный; **Statement** — «Система должна…»; **Acceptance** — критерий приёмки; **Verification** — метод. AREA ∈ {FUNC, INT, PERF, SEC, REL, AVAIL, OBS, COMP, INST, BUILD, DIST, MAINT, REUSE, PORT, COST, DEAD, POC, CM, ML}.

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

- **REQ-INT-003** — GUI должен предоставлять: выбор MIDI и текста, редактор слог-нота, выбор RVC-модели/индекса, кнопки «Рендер», «Прослушать», «Экспорт», индикаторы прогресса и ошибок.
  *Acceptance:* сквозной сценарий «импорт → рендер → прослушивание → экспорт» выполняется без CLI; ошибки ввода показываются текстом и не приводят к падению. *Verification:* Demonstration.
- **REQ-INT-004** — GUI должен работать без доступа к сети и сохранять последнюю сессию (пути, модель, настройки голоса) между запусками.
  *Acceptance:* после перезапуска открывается тот же проект и параметры. *Verification:* Test.
- **REQ-INT-005** — Все длительные операции (рендер, конверсия тембра) должны быть отменяемыми и не блокировать интерфейс.
  *Acceptance:* отмена в любой момент, GUI отзывчив (реакция на клик ≤ 100 мс). *Verification:* Test.

### 3.2 Функциональные требования {#32-functional}

- **REQ-FUNC-001** — Система должна строить фонемную последовательность из текста для русского и английского языков с привязкой к нотам и автоматическим распределением длительностей.

- **REQ-FUNC-004** — Система должна выполнять перенос тембра RVC: извлечение контент-признаков, оценку F0, поиск по индексной базе и генерацию сигнала целевым тембром.
  *Acceptance:* сходство тембра (косинус эмбеддингов спикера) ≥ 0.75; сохранение мелодии и разборчивости лирики. *Verification:* Test.
- **REQ-FUNC-005** — Система должна позволять управлять тембром: сила переноса, формантный сдвиг, дыхательность, питч-сдвиг в полутонах, индексный поиск (on/off, ratio).
  *Acceptance:* изменение каждого параметра слышимо и воспроизводимо; значения сохраняются в пресете. *Verification:* Demonstration/Test.
- **REQ-FUNC-006** — Система должна выполнять DSP-постобработку и экспорт в WAV/FLAC (44.1/48 кГц, 16/24 бит) с именованием файлов по шаблону.

- **REQ-FUNC-007** — Система должна поддерживать real-time live-мониторинг: озвучивание нот по MIDI-вводу выбранным тембром.
  *Acceptance:* нота воспроизводится выбранным тембром; при перегрузке — грациозная деградация без падения. *Verification:* Demonstration.
- **REQ-FUNC-008** — Система должна обеспечивать пакетный офлайн-рендер нескольких партий/пресетов и формирование отчёта о рендере.
  *Acceptance:* отчёт содержит длительность, RTF, использованную модель и её версию. *Verification:* Test.
- **REQ-FUNC-009** — Система должна обнаруживать и корректно обрабатывать негативные сценарии: пустой текст, ноты вне вокального диапазона модели, несовпадение языка.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

- **REQ-PERF-001** — Офлайн-рендер на 8-ядерном CPU (AVX2) должен иметь RTF ≤ 0.15 при 48 кГц без GPU; при наличии GPU (CUDA/DirectML) — RTF ≤ 0.05.
  *Acceptance:* измерение на эталонной 3-минутной композиции, 3 прогона, медиана. *Verification:* Test.
- **REQ-PERF-002** — Сквозная задержка real-time режима (вход MIDI → выход аудио) должна быть ≤ 250 мс при буфере 128–256 сэмплов, 48 кГц.
  *Acceptance:* измерение loopback-методом; на целевом ПК ≤ 250 мс. *Verification:* Test.
- **REQ-PERF-003** — Пиковая оперативная память на один поток синтеза должна быть ≤ 4 ГБ; время загрузки модели — ≤ 10 с.
  *Acceptance:* замеры на эталонном ПК без swap-активности. *Verification:* Test.

#### 3.3.2 Безопасность {#332-security}

- **REQ-SEC-001** — Система должна работать полностью офлайн: никакой передачи голосовых данных, моделей и лирики по сети без явного действия пользователя.
  *Acceptance:* сетевой трафик при штатной работе отсутствует (проверка монитором). *Verification:* Analysis/Test.
- **REQ-SEC-002** — Система должна проверять целостность моделей (хеш) и не исполнять произвольный код из файлов моделей.
  *Acceptance:* подмена файла модели обнаруживается при загрузке. *Verification:* Test.
- **REQ-SEC-003** — Система должна хранить согласие владельца голоса и метаданные модели (владелец, дата, лицензия) локально и показывать их перед рендером.
  *Acceptance:* рендер без зафиксированного согласия блокируется с объяснением. *Verification:* Inspection.

#### 3.3.3 Надёжность {#333-reliability}

- **REQ-REL-001** — Система не должна терять данные сессии при сбое: проект сохраняется атомарно, несохранённый прогресс восстанавливается.

  *Acceptance:* длительная сессия 1 ч под нагрузкой 90 % CPU. *Verification:* Test.
- **REQ-REL-003** — При ошибке обработки одного фрагмента система должна продолжать рендер остальных и помечать проблемный участок в отчёте.
  *Acceptance:* искусственно повреждённый фрагмент не прерывает весь рендер. *Verification:* Test.

#### 3.3.4 Доступность {#334-availability}

- **REQ-AVAIL-001** — Готовность к работе в течение сессии: время запуска приложения до готовности GUI ≤ 5 с, до готовности real-time движка с загруженной моделью ≤ 15 с.

  *Acceptance:* без подтверждения файл не создаётся (в GUI); в CLI — флаг `--yes`. *Verification:* Test.
- **REQ-ML-011** — Пользователь должен иметь ручную коррекцию мелодии (правка F0/длительностей) после переноса тембра без повторного обучения модели.
  *Acceptance:* правка применяется за ≤ 1 с к выбранному фрагменту. *Verification:* Demonstration.

#### 3.6.6 Жизненный цикл модели и операции {#366-model-lifecycle-and-operations}

- **REQ-ML-012** — Модели должны версионироваться и поставляться отдельно от ядра; при деградации качества возможен откат на предыдущую версию модели без обновления приложения.
  *Acceptance:* переключение версии модели в настройках/CLI. *Verification:* Test.
- **REQ-ML-013** — Для каждого релиза модели должен фиксироваться оценочный набор и отчёт метрик (REQ-ML-002/003) для воспроизводимости сравнений.
  *Acceptance:* артефакты оценки в репозитории/CI с хешами набора. *Verification:* Inspection.
